## 상태를 읽는 위치가 범위를 정한다

리컴포지션 범위는 상태를 **어디서 읽느냐**로 정해진다. 같은 상태라도 람다 안에서 읽으면 그 람다만 다시 돈다.

```kotlin
@Composable
fun Counter(count: State<Int>) {
    Column {
        Header()
        Text("${count.value}")
    }
}
```

## 스킵이 되는 조건

파라미터가 전부 안정적이고 이전 값과 같으면 함수 본문을 건너뛴다. 불안정한 타입 하나가 섞이면 스킵이 깨진다.

> [!tip] 안정성 확인
> 컴포즈 컴파일러 리포트를 켜면 함수별로 skippable 여부를 볼 수 있다.

## 정리

상태를 읽는 지점을 아래로 내릴수록 다시 그리는 범위가 좁아진다. 성능 문제의 절반은 여기서 풀린다.
