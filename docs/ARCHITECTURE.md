# Haeti.log 아키텍처

Compose Multiplatform 하나로 두 앱을 만듭니다. 방문자가 보는 블로그는 Kotlin/Wasm으로 빌드해 GitHub Pages에
올리고, 글을 쓰는 어드민은 내 Mac에서만 도는 JVM 데스크톱 앱입니다.

## 설계 기준

글은 두세 달에 한 편 쓰고, 관리는 혼자 합니다. 그래서 판단이 갈릴 때 아래 세 가지를 기준으로 삼았습니다.

1. **운영할 서버가 없어야 한다.** 서버가 생기면 비용, 보안 패치, 장애 대응이 같이 따라옵니다.
   글 몇 편을 보여 주는 데 그만한 비용을 들일 이유가 없습니다.
2. **몇 달 만에 열어도 빌드돼야 한다.** 오랜만에 글을 쓰려고 열었는데 깨져 있으면 안 됩니다.
   그래서 실수를 런타임보다 컴파일이나 빌드 단계에서 잡는 쪽을 고릅니다.
3. **글 쓰는 과정은 짧아야 한다.** 글 하나는 폴더 하나이고, 폴더를 추가하는 것 말고 할 일이 없어야 합니다.

`haeti.kmp.feature`, `haeti.spotless`)로 모았습니다. 새 모듈은 `plugins { }` 한 줄로 시작합니다.

## 결정

### 1. 글은 저장소의 마크다운 파일로 두고, 빌드할 때 정적 파일로 만든다

**상황.** 글을 어디에 저장하고 블로그가 어떻게 읽어 올지 정해야 했습니다.

**선택지.** 백엔드와 DB를 두는 방법, 외부 CMS API를 런타임에 부르는 방법, 저장소의 마크다운 파일을
빌드할 때 함께 배포하는 방법이 있었습니다.

**결정.** 마지막 방법을 골랐습니다. 앞의 둘은 서버나 외부 서비스에 기대게 되어 기준 1에 맞지 않습니다.
`PostsResourcesTask`가 `content/posts/`를 훑어 초안(`draft: true`)을 빼고 `build/` 아래로 복사한 뒤,
최신순 목록인 `index.json`을 만듭니다. 이 디렉터리를 Compose Resources의 `customDirectory`로 연결해서
생성물이 소스 트리나 git에 섞이지 않게 했습니다. 배포하면 글은 wasm 번들 옆에 정적 파일로 실리고,
앱은 필요할 때 `Res.readBytes`로 읽어 와 메모리에 캐시합니다.

**감수한 것.** 오타 하나를 고쳐도 다시 빌드하고 배포해야 하고, 반영까지 몇 분이 걸립니다.
서버가 없으니 글 검색 같은 기능은 브라우저 안에서 해결해야 합니다.

### 2. 어드민은 로컬 데스크톱 앱이고, 저장소가 곧 DB다

**상황.** 마크다운을 편집기에서 바로 쓰면 이미지 크기 지시어나 콜아웃이 실제로 어떻게 보이는지 알 수 없었습니다.

**결정.** 파일을 직접 읽고 쓰는 데스크톱 앱을 만들었습니다. 웹 어드민이면 로그인과 저장 API, 즉 서버가
필요합니다. 로컬 앱은 디스크의 파일만 고치면 되고, 버전 관리와 백업은 git이 맡습니다. 미리보기는 블로그와
같은 `core:markdown` 렌더러를 써서, 미리보기와 실제 화면이 어긋날 일이 없습니다.
`core:*`와 `feature:*`를 jvm과 wasmJs 양쪽으로 컴파일하는 이유가 이것입니다.

**감수한 것.** 이 Mac에서만 글을 쓸 수 있습니다. 어드민이 배포물에 섞이지 않도록 `app:web`과 `app:admin`은
서로 의존하지 않게 막았습니다.

### 3. 캔버스라서 생기는 빈자리는 빌드할 때 만드는 HTML로 채운다

**상황.** Compose 웹은 화면 전체를 `<canvas>` 하나에 그립니다. HTML에 글 내용이 없으니 카카오톡이나 슬랙에
링크를 붙여도 미리보기가 안 뜨고, 검색 엔진도 글을 알 수 없습니다. GitHub Pages는 모르는 경로를 404로
돌려주기 때문에 `/post/<slug>` 주소로 바로 들어오거나 새로고침하는 것도 문제였습니다.

**결정.** 서버 렌더링은 기준 1 때문에 할 수 없으니, 빌드 단계에서 정적 파일을 만듭니다.
`SiteFilesTask`가 글마다 `post/<slug>/index.html` 셸(제목, 요약, OG 이미지)을 만들고, `sitemap.xml`,
RSS(`feed.xml`), `robots.txt`, 그 밖의 경로를 받는 `404.html`도 함께 만듭니다. 셸이 실제 파일이라 딥링크도
200으로 열립니다. OG 이미지는 썸네일이 있으면 그것을, 없으면 블로그 목록과 같은 표지 그림을 그려서 씁니다.

**감수한 것.** 셸에는 요약까지만 있고 본문은 없어서, 검색 엔진은 본문 내용으로 글을 찾지 못합니다.
브라우저의 페이지 내 검색(⌘F)과 스크린리더도 캔버스 안의 글자를 읽지 못합니다.

### 4. 계층은 나누되 블로그 크기에 맞게 줄인다

**상황.** 화면은 홈, 글, 소개·프로젝트 세 종류이고, 데이터는 읽기 전용에 가깝습니다.

**결정.** 모듈 경계는 지키되 이 규모에서 일만 늘리는 단계는 뺐습니다.

- **도메인(유스케이스) 레이어를 두지 않았습니다.** `Repository → ViewModel`이 이미 한 단계라
  유스케이스를 끼우면 위임만 늘어납니다. 필요해지면 `core:domain`을 얹으면 됩니다.
- **feature 모듈을 api/impl로 쪼개지 않았습니다.** 화면 셋에 모듈 여섯 개는 과합니다. 화면 사이 이동은
  `core:navigation`에 모은 `NavKey`로 해서, feature끼리 서로 몰라도 됩니다.
- **백스택은 하나만 둡니다.** 탭마다 히스토리를 따로 기억할 이유가 없는 블로그입니다.
- **플랫폼별 코드는 `expect`/`actual` 네 곳뿐입니다.** 나머지는 전부 `commonMain`에 있습니다.

**감수한 것.** 화면이 많아지면 `core:navigation`이 모든 목적지를 알게 되고, 그때는 나눠야 합니다.

### 5. 실수를 컴파일 단계에서 잡는 도구를 고른다

기준 2를 적용한 결정들입니다.

- **DI는 Koin에서 Metro로 바꿨습니다.** Koin은 런타임에 의존성을 찾기 때문에, 바인딩이 빠지면 앱을
  실행해서 그 화면을 열어 봐야 알 수 있습니다. Metro는 컴파일할 때 그래프 전체를 확인해서 빠진 바인딩이
  곧바로 컴파일 에러가 되고, jvm과 wasmJs에서 똑같이 동작합니다.
- **내비게이션은 직접 만든 라우터에서 Navigation 3로 바꿨습니다.** `sealed Route`와 수동 백스택은 화면 두 개일
  때는 충분했지만, 목적지가 다섯 개로 늘고 상태 저장과 복원이 필요해지자 직접 관리할 부분이 너무 많았습니다.
  브라우저 주소와의 동기화(`pushState`/`popstate`)는 `app:web`에서 직접 하고, 경로와 `NavKey`를 오가는
  변환은 순수 함수로 두어 브라우저 없이 테스트합니다.
- **날짜는 문자열 대신 `LocalDate`로 다룹니다.** 문자열이면 정렬이나 형식 실수를 컴파일러가 잡지 못합니다.

**감수한 것.** Metro는 비교적 새 도구라 참고할 자료가 적습니다. Navigation 3의 멀티플랫폼 UI는 JetBrains가
따로 내는 버전이라 Google 쪽과 버전이 따로 갑니다.

### 6. 번역이 최신인지는 해시로 확인한다

**상황.** 글은 한국어 원문(`index.md`)과 영어 번역(`index.en.md`)으로 나갑니다. 원문을 고치면 번역이
뒤처졌는지 알아야 하는데, 사람이 기억하는 방식으로는 빠뜨리기 쉽습니다.

**결정.** 번역 파일의 `source:`에 번역할 당시 원문의 지문(제목·요약·본문을 이은 SHA-256 앞 12자리)을
적습니다. 빌드 태스크 `checkTranslations`와 어드민이 지금 원문의 지문과 비교해서, 다르면 "갱신 필요"로
표시합니다. CI에서도 같은 검사를 돌립니다.

**감수한 것.** 띄어쓰기 하나만 고쳐도 갱신 필요로 바뀝니다. CI는 지금 경고만 남기고 빌드를 막지는 않습니다.

### 7. 테스트는 공통 코드에 두고 JVM에서 돌린다

**결정.** core와 feature의 테스트는 `commonTest`에 두고 `./gradlew jvmTest`로 실행합니다. 브라우저 테스트는 Chrome 기반
러너가 필요해서 꺼 두었습니다. 플랫폼에 묶인 코드는 JVM 테스트로 따로 둡니다. 어드민의 파일 저장과 이미지 처리는
`app:admin`의 `test`, Skia 코덱이 필요한 애니메이션 프레임은 `core:markdown`의 `jvmTest`, 사이트 파일 생성은
`build-logic`의 `test`에 있고, CI는 세 갈래를 모두 돌립니다. 대신 테스트 소스도 wasmJs로 컴파일되기 때문에, 두 플랫폼에서 API가 어긋나면
컴파일 단계에서 드러납니다. 가짜 저장소와 고정 데이터는 `core:testing`에 모았고, Flow는 Turbine으로 검증합니다.

**감수한 것.** 캔버스 렌더링과 브라우저 히스토리처럼 실제 브라우저에서만 확인되는 동작은 자동 테스트 밖에
있어서, 직접 띄워서 확인합니다.

화면은 상태에 따라 로딩, 목록, 오류를 그립니다.

## 웹에서 따로 처리한 것

- **폰트:** 폰트가 도착하기 전에 첫 화면을 그리면 한글이 □로 굳습니다. 폰트 세 개가 모두 준비될 때까지
  첫 페인트를 미룹니다.
- **줄바꿈:** 캔버스의 텍스트 엔진은 한글 음절 사이 어디서든 줄을 바꿉니다. 화면에 표시하는 문자열에만
  글자 사이에 WORD JOINER(U+2060)를 넣어 단어 단위로 줄이 바뀌게 했습니다.
- **배포 경로:** GitHub Pages는 `/저장소명/` 아래에 올라갑니다. 빌드할 때 이 경로를 `<base href>`에 넣고,
  라우팅과 리소스 경로는 모두 이 값을 기준으로 계산합니다. 커스텀 도메인으로 옮겨도 빌드 인자 하나만
  바꾸면 됩니다.
- **미지원 브라우저:** `index.html`이 WasmGC 지원부터 확인하고, 지원하지 않으면(Safari 18.2 이전 등)
  번들을 받지 않고 안내 문구를 보여 줍니다.
